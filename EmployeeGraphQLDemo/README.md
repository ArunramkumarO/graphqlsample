## Setup

Prerequisites: .NET 10 SDK and SQL Server LocalDB (installed with Visual Studio) or any SQL Server.
If you use another server, edit `ConnectionStrings:DefaultConnection` in `appsettings.json`.

From scratch (the files in this folder are already the result of these steps):

```bash
mkdir EmployeeGraphQLDemo && cd EmployeeGraphQLDemo
dotnet new webapi --use-controllers
dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 10.0.12
dotnet add package Microsoft.EntityFrameworkCore.Design --version 10.0.12
dotnet add package GraphQL --version 8.8.5
dotnet add package GraphQL.SystemTextJson --version 8.8.5
dotnet add package GraphQL.Server.Transports.AspNetCore --version 8.3.3
dotnet add package GraphQL.Server.Ui.GraphiQL --version 8.3.3
dotnet add package Swashbuckle.AspNetCore --version 10.3.0
```

Then, in this folder:

```bash
dotnet tool install --global dotnet-ef
dotnet restore
dotnet ef migrations add InitialCreate
dotnet ef database update
dotnet run
```

Open the URL printed by `dotnet run` and add:

- Swagger (REST): `/swagger`
- GraphQL endpoint: `/graphql` (POST)
- GraphiQL (GraphQL UI in the browser): `/graphiql`

## API documentation

- **REST:** `/swagger`. Descriptions come from the `///` comments in `EmployeesController.cs` and `Employee.cs`
  (XML docs are generated by `GenerateDocumentationFile` and loaded with `IncludeXmlComments` in `Program.cs`).
- **GraphQL:** `/graphiql`, **Docs** panel (book icon). Descriptions come from `.Description("...")` in the
  `GraphQL/` files. GraphQL publishes them automatically through *introspection*: the schema describes itself.

## Request flow

```
GraphQL client (GraphiQL / Postman / app)
      │  POST /graphql   { "query": "...", "variables": {...} }
      ▼
/graphql endpoint        ← app.UseGraphQL<EmployeeSchema>("/graphql") in Program.cs
      ▼
GraphQL.NET              parses the text, validates it against the schema
      ▼
Schema (EmployeeSchema)  "query" → EmployeeQuery, "mutation" → EmployeeMutation
      ▼
Query / Mutation field   e.g. the `employee` field
      ▼
Resolver                 the lambda on that field; reads arguments, uses AppDbContext
      ▼
EF Core                  turns LINQ into SQL
      ▼
SQL Server
```

On the way back, GraphQL.NET keeps only the fields the client asked for and serializes them to JSON.

## The GraphQL files

| File | What / why / how |
|---|---|
| `Models/Employee.cs` | Plain C# class; EF Core maps it to a table. GraphQL knows nothing about it until `EmployeeType` describes it. |
| `GraphQL/EmployeeType.cs` | Declares the GraphQL type `Employee` and its fields. GraphQL.NET only allows clients to request fields listed here. Each `Field(x => x.Name)` reads that property from the `Employee` object EF Core loaded. |
| `GraphQL/EmployeeQuery.cs` | Root `Query` type: read operations (`employees`, `employee(id)`). Each has a resolver that gets `AppDbContext` from `context.RequestServices` and queries EF Core. |
| `GraphQL/EmployeeMutation.cs` | Root `Mutation` type: write operations. Resolvers add/modify/remove through `AppDbContext`, call `SaveChangesAsync()`, and return the entity. |
| `GraphQL/EmployeeSchema.cs` | Ties the Query and Mutation roots together. GraphQL.NET runs every request against this one schema. |
| `Program.cs` | Registers everything and exposes `/graphql`. |

Why `RequestServices` in the resolvers? The schema is built once and shared (singleton), but `AppDbContext` is scoped
(one per HTTP request). Resolving it per call avoids a long-lived DbContext.

### Program.cs, line by line

```csharp
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(...));
```
EF Core with SQL Server, scoped per request.

```csharp
builder.Services.AddGraphQL(graphql => graphql
    .AddSchema<EmployeeSchema>()
    .AddSystemTextJson()
    .AddGraphTypes(typeof(EmployeeSchema).Assembly));
```
- `AddGraphQL(...)` – adds GraphQL.NET's services (executor, validation, etc.) and gives a builder to configure them.
- `AddSchema<EmployeeSchema>()` – registers our schema (this is the modern replacement for the old
  `services.AddSingleton<ISchema, EmployeeSchema>()`; it does that registration and more).
- `AddSystemTextJson()` – how request/response JSON is read and written.
- `AddGraphTypes(assembly)` – scans the assembly and registers every graph type (`EmployeeType`, `EmployeeQuery`,
  `EmployeeMutation`) in DI so the schema can create them.

```csharp
app.UseGraphQL<EmployeeSchema>("/graphql");
app.UseGraphQLGraphiQL("/graphiql");
```
Middleware: handles requests at `/graphql` using that schema; serves a browser UI at `/graphiql`.

## GraphQL vs REST (same Employee operations)

| | REST | GraphQL |
|---|---|---|
| List | `GET /api/employees` | `query { employees { id name department } }` |
| One | `GET /api/employees/1` | `query { employee(id: 1) { name } }` |
| Create | `POST /api/employees` | `mutation { createEmployee(...) { id } }` |
| Update | `PUT /api/employees/1` | `mutation { updateEmployee(id: 1, ...) { id } }` |
| Delete | `DELETE /api/employees/1` | `mutation { deleteEmployee(id: 1) }` |
| URLs | one per resource/action | one (`/graphql`) |
| Response shape | fixed by the server (all 6 fields) | chosen by the client |

Why can the client choose fields? The query text is parsed *by the server* and matched against the schema; GraphQL.NET
then only executes and returns the selected fields. Ask for `id name` and you get exactly `id` and `name`. With REST the
server returns whatever the action returns (over-fetching), or you need extra endpoints.

## Vocabulary

- **Schema** – the contract: every type and operation the API offers (`EmployeeSchema`).
- **Type** – a shape of data, e.g. `Employee`, `String`, `Int`.
- **Field** – a named piece of a type, e.g. `Employee.name`. Queries select fields.
- **Query** – a read operation (like GET).
- **Mutation** – a write operation (like POST/PUT/DELETE); the top-level fields run one after another.
- **Resolver** – the C# code that produces a field's value (the `ResolveAsync` lambda).
- **Arguments** – inputs on a field: `employee(id: 1)`.
- **Variables** – arguments sent separately as JSON so the query text stays constant (see below).

## Learning exercise

1. **PhoneNumber** – add `public string? PhoneNumber { get; set; }` to `Employee`, add `Field(x => x.PhoneNumber, nullable: true)`
   to `EmployeeType`, then `dotnet ef migrations add AddPhoneNumber` and `dotnet ef database update`.
2. **`employeesByDepartment` query** – in `EmployeeQuery`, add a field with a `NonNull String` argument `department`.
   The resolver does `db.Employees.Where(e => e.Department == dept).ToListAsync()`.
3. **Filtering** – make the `department` argument optional on `employees` (`Argument<StringGraphType>("department")`);
   in the resolver, apply `Where` only if `context.HasArgument("department")`.
4. **`EmployeeInput`** – create `class EmployeeInputType : InputObjectGraphType<Employee>` with
   `Field(x => x.Name)` etc. Input types are separate from output types because inputs can't have resolvers or cycles.
5. **Use it in create** – replace the five arguments with
   `.Argument<NonNullGraphType<EmployeeInputType>>("employee")` and read it with `context.GetArgument<Employee>("employee")`.
   The client then sends `createEmployee(employee: { name: "John", ... })`.
